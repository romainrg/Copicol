# Contributing to Copicol

Thanks for your interest in Copicol! This guide explains how to set up the project, the rules every change follows, and how pull requests are reviewed.

By taking part, you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Ways to contribute

- **Report a bug**: open an issue with the *Bug report* template, after checking that it has not been reported already.
- **Suggest a feature**: open an issue with the *Feature request* template. For anything bigger than a small fix, discuss it in an issue **before** writing code, so we agree on the approach first.
- **Fix or build something**: issues labeled [`good first issue`](https://github.com/romainrg/Copicol/labels/good%20first%20issue) and [`help wanted`](https://github.com/romainrg/Copicol/labels/help%20wanted) are good starting points. Comment on the issue to say you are working on it.
- **Improve the docs or translate the app**: English localization is the most wanted contribution.
- **Report a security issue privately**, never in a public issue: see [SECURITY.md](SECURITY.md).

## Development setup

Requirements: macOS 14 or later, Xcode 16 or later and [XcodeGen](https://github.com/yonaskolb/XcodeGen) (`brew install xcodegen`).

```sh
git clone https://github.com/<your-account>/Copicol.git
cd Copicol
xcodegen generate        # creates Copicol.xcodeproj from project.yml
open Copicol.xcodeproj   # or use the commands below
```

| Task | Command |
|---|---|
| Build (Debug) | `xcodebuild -project Copicol.xcodeproj -scheme Copicol -configuration Debug -derivedDataPath build build` |
| Run | `open build/Build/Products/Debug/Copicol.app` |
| All tests | `xcodebuild test -project Copicol.xcodeproj -scheme Copicol -derivedDataPath build -destination 'platform=macOS'` |
| Core tests only (faster) | `swift test --package-path CopicolCore` |
| Universal release zip | `scripts/build-release.sh` |
| Regenerate the README images | `scripts/screenshots.sh` |

Good to know:

- `project.yml` is the source of truth. Run `xcodegen generate` again after adding, removing or renaming a file. Never commit `Copicol.xcodeproj` and never edit `Copicol/Resources/Info.plist`: both are generated.
- If `xcodebuild` complains that it requires Xcode while the Command Line Tools are selected, prefix the commands with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`.
- Development builds are signed ad hoc, and macOS ties the Accessibility permission to the build's signature. After each rebuild, remove Copicol from System Settings › Privacy & Security › Accessibility and allow it again to test direct paste. *Copy only* mode (Settings › Général) avoids this while you work on other things.
- A development build uses the same bundle identifier, and therefore the same history, as an installed Copicol. Quit the installed app before running yours.

## Project structure

| Path | Contents |
|---|---|
| `CopicolCore/` | Swift package with all the testable logic: SwiftData models, pasteboard reading and writing, storage, deduplication, retention, search and the iCloud mirror. |
| `CopicolCore/Tests/CopicolCoreTests/` | Unit tests (XCTest). |
| `Copicol/` | The app target: system integration and UI (shelf, global shortcut, paste service, settings, menu bar, onboarding). |
| `Tools/Screenshots/` | Development tool that renders the README images from the real views. |
| `scripts/` | Release, screenshot, release-notes and icon scripts. |
| `docs/` | Architecture and release documentation, images. |

Read [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) before changing storage, capture or sync.

## Rules for every change

These rules keep Copicol small, private and maintainable. A change that breaks one of them needs to be discussed in an issue first.

### Product and privacy

- No third-party dependencies: Apple frameworks only.
- No analytics, telemetry, crash reporting or new network access. The only network use is link previews (LinkPresentation) for links the user copied, plus the opt-in iCloud sync.
- Never record pasteboard content marked `org.nspasteboard.ConcealedType`, `org.nspasteboard.TransientType` or `org.nspasteboard.AutoGeneratedType`, and always honor the excluded apps.
- Never log clipboard contents.
- The app stays sandboxed. Adding an entitlement requires a discussion in an issue.
- Do not change the bundle identifier, the exported UTType or the iCloud container: users would lose their history and their permissions.

### Code

- Business logic lives in `CopicolCore`, with unit tests. The app target only holds UI and system integration.
- MVVM with `@Observable`. No new singletons: `ClipboardMonitor.shared` is the only one, because there is only one general pasteboard.
- SwiftUI first, AppKit where SwiftUI is not enough (panels, pasteboard, status item, keyboard events).
- `ClipStore`, the view models and the UI run on the main actor. Hashing and image processing run off the main thread, on `Sendable` values.
- Models in the *Boards* container must stay CloudKit-compatible: a default value for every property, no unique constraints, no relationships. Schema changes must remain lightweight migrations, so new properties need a default value.
- Swift 5 language mode on the Swift 6 toolchain. The build must stay free of warnings.
- Follow the existing style: 4-space indentation, `// MARK: -` sections, small focused types.
- Code comments and documentation comments are written in **French**; identifiers and API names in **English**. User-facing strings are in French until localization lands.

### Tests

- Every logic change in `CopicolCore` comes with tests. A bug fix comes with a test that fails without the fix.
- Tests never touch the real general pasteboard or the user's data: use the helpers in `TestSupport.swift` (private named pasteboards, in-memory containers, controllable clock).
- The UI (shelf, paste, windows) has no automated tests, because driving it requires the Accessibility and Screen Recording permissions. Describe your manual test steps in the pull request.

## Commits and branches

- Work on a branch of your fork, created from `main`: `feat/short-description`, `fix/short-description`, `docs/short-description`…
- Write [Conventional Commits](https://www.conventionalcommits.org/): `feat: …`, `fix: …`, `docs: …`, `refactor: …`, `test: …`, `perf: …`, `build: …`, `ci: …` or `chore: …`. Use the imperative mood, keep the subject under 72 characters, and reference issues in the body (`Fixes #42`).
- Keep commits focused, and rebase on `main` rather than merging `main` into your branch.

## Pull requests

1. One topic per pull request. Prefer small pull requests (a few hundred lines) and split larger work.
2. Fill in the pull request template, including how you tested and screenshots (light and dark appearance) for any UI change.
3. Make sure `xcodebuild test` passes and the build has no warnings. CI runs the tests and a universal Release build on every pull request.
4. Add a line to `CHANGELOG.md` under **Unreleased** for any user-visible change.
5. Update the documentation (README, `docs/`, `AGENTS.md`) when behavior, commands or rules change. If the shelf looks different, regenerate the images with `scripts/screenshots.sh`.
6. Do not change the version number: the maintainer handles releases.

The maintainer reviews every pull request. Questions and change requests are a normal part of review, not a rejection. Pull requests are squash-merged, so their title must be a valid Conventional Commit message.

## AI-assisted contributions

AI coding assistants are welcome. [AGENTS.md](AGENTS.md) gives them the project's commands and rules (Claude Code reads it through `CLAUDE.md`).

- You are responsible for every line you submit: read it, understand it and test it.
- Say in the pull request which tool you used, and for what.
- Do not submit unreviewed bulk changes, images that do not show the real app, or code you cannot explain.
